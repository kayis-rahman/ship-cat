# Discord bridge

The Raspberry Pi process is started with `node src/discord-bridge-service.js`. It requires explicit `SHIPCAT_BRIDGE_HOST`, `SHIPCAT_BRIDGE_TOKEN`, `SHIPCAT_BRIDGE_QUEUE`, and absolute `SHIPCAT_DISCORD_CLIENT_MODULE` settings; `SHIPCAT_BRIDGE_PORT` defaults to 8765. The service host must be a private-network IP, never loopback, wildcard, or public. The client module must export the already-authenticated Discord client and `captainUserId`; it is supplied and managed by the captain. Shipcat does not log in or read Discord credentials. Message Content Intent and account setup remain captain-managed.

`DiscordEventSource` consumes `messageCreate` events and normalizes them before queue insertion. Non-voice records contain only message ID, channel ID, human-author flag, timestamp, and message text. Usernames, user IDs, avatars, embeds, attachment metadata, and raw payloads are discarded. Non-voice attachments are ignored. The queue atomically persists candidate state and retains pending message IDs. After acknowledgement it retains only the message ID and acknowledgement time for 30 days, then expires that deduplication record.

Voice messages are accepted only from the configured captain user ID. The queue persists only message and channel IDs plus the approved minimal event fields. On each audio request, the authenticated client refetches the voice message by those IDs, revalidates its captain author and voice type, and streams its audio bytes to the Mac without persisting or caching a URL or audio. A missing source is logged without message data and dropped. `MacPuller` downloads into a temporary local file, invokes `mlx_whisper` with an explicitly configured local model directory, and removes the file on both success and failure. There is no cloud fallback. Only the transcript text is sent onward.

Mac handoff is an explicitly configured absolute executable path passed as `handoffCommand`. It receives one minimized JSON message on stdin; Shipcat does not discover commands or write Firstmate state. If no command is configured, polling sends and acknowledges nothing. Command failures leave events pending for retry; message IDs are stable for downstream idempotency. The cursor is atomically saved only after successful handoff and bridge acknowledgement.

Tests use synthetic message events, synthetic local audio responses, and a fake local MLX module. They do not log into Discord, make Discord/CDN requests, use real credentials, or start/deploy a Pi service.
